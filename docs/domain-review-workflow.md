# POLARIS Expert Domain Review Workflow & Provenance Integrity

## 1. Overview & Core Philosophy

The **POLARIS Antarctic Vessel Navigation System** relies on a three-tier dataset evidence pipeline:
1. **Sourced Data:** Real Antarctic hydrographic observations (USNIC iceberg positions, Copernicus CMEMS sea-ice grids, ECMWF ERA5 wind and ocean current reanalysis).
2. **Explicit Simulation:** Controlled Nomoto vessel kinematics, route variations, and atmospheric visibility perturbations.
3. **Expert Domain Validation:** Direct evaluation, annotation, and verification by polar maritime experts (watch officers, ice pilots, polar navigators).

> [!CAUTION]
> **POLARIS must NEVER learn merely from its own experimental heuristics.**
> The initial labels in the 500-scenario corpus are generated by an experimental rule baseline (`scratch/polaris_rule_baseline.py`) and are explicitly tagged:
> $$\text{LabelSource} = \text{EXPERIMENTAL\_RULE\_BASELINE}$$
> They are **NOT** expert-validated. Laya model training is strictly **PROHIBITED** until domain experts review, annotate, and validate the dataset.

## 2. Provenance Architecture

To prevent synthetic vessel scenarios from mimicking historical voyage logs, every scenario explicitly distinguishes environmental anchors from simulated state:

```text
                        ┌──────────────────────────────────────────────┐
                        │      Real Antarctic Environmental Anchor     │
                        │  - USNIC Iceberg Catalogue                   │
                        │  - Copernicus CMEMS Sea-Ice Grid             │
                        │  - ECMWF ERA5 Wind & Current Vectors         │
                        └──────────────────────┬───────────────────────┘
                                               │
                                               ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                 POLARIS Nomoto Vessel Kinematics Engine                     │
│  - Controlled perturbation of vessel speed, heading, and route geometry     │
│  - Seed-controlled atmospheric visibility model                             │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│             PolarisDomainScenario (SourceType: REAL_SOURCE_DERIVED_SIMULATED)│
│  - Field-Level Provenance Details                                           │
│  - Baseline Action (LabelSource: EXPERIMENTAL_RULE_BASELINE)                │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Field-Level Provenance Breakdown
- **`iceberg_position` / `iceberg_dimensions`:** `USNIC / POLARIS Engine` (`SOURCE_DERIVED`)
- **`sea_ice_concentration`:** `Copernicus CMEMS` (`SOURCE_DERIVED`, bilinear interpolation)
- **`wind_conditions` / `current_conditions`:** `ECMWF ERA5` (`REANALYSIS`)
- **`visibility_conditions` / `vessel_kinematics`:** `POLARIS Sim` (`SIMULATED`)
- **`route_blockage_status`:** `POLARIS Nav Controller` (`MODELLED`)

## 3. Local Domain Review Application & Interface

A dedicated developer/domain-review application is served locally via FastAPI:

### Service Architecture & Port Binding
- **Laya Decision Engine API:** `http://127.0.0.1:8000`
- **POLARIS Backend & Domain Review Portal:** `http://127.0.0.1:8001`
- **Review Portal Interface URL:** `http://127.0.0.1:8001/review`

### Review Interface Display
1. **Telemetry & Environment:** Vessel speed, heading, destination distance, fuel, nearest iceberg distance, sea ice concentration, thickness, route blockage, wind, current, visibility, water temp, emergency status.
2. **Provenance Anchor:** Sourced provider, dataset name, record ID, and observation timestamp.
3. **Experimental Baseline Banner:** Prominently displays the baseline recommendation with a mandatory **`NOT EXPERT VALIDATED`** safety pill.
4. **Expert Action Selector:**
   - `CONTINUE`
   - `SLOW DOWN`
   - `REROUTE`
   - `HOLD POSITION`
   - `REQUEST ESCORT`
   - `EMERGENCY RESPONSE`
   - `AMBIGUOUS / INSUFFICIENT INFO`
5. **Reviewer Confidence:** 1 (Very Low) to 5 (Very High).
6. **Key Driving Factors:** Checkboxes for iceberg proximity, sea ice concentration, visibility, wind, current, route blockage, emergency condition, etc.
7. **Rationale & Additional Information:** Text prompts for decision rationale and missing information.

## 4. Multi-Reviewer Support & Consensus Rules

Multiple polar mariners may review the same scenario independently. The workflow preserves all individual annotations:

- **Single Reviewer:**
  $$\text{label\_source} = \text{EXPERT}, \quad \text{consensus\_action} = \text{selected\_action}, \quad \text{disagreement\_flag} = \text{False}$$
- **Majority Consensus ($>50\%$ agreement):**
  $$\text{label\_source} = \text{CONSENSUS}, \quad \text{consensus\_action} = \text{most\_common}, \quad \text{disagreement\_flag} = \text{False}$$
- **Disagreement / No Majority:**
  $$\text{consensus\_action} = \text{null}, \quad \text{reviewer\_status} = \text{AMBIGUOUS}, \quad \text{disagreement\_flag} = \text{True}$$

Individual reviewer annotations (`reviewer_id`, `selected_action`, `confidence`, `rationale`, `reviewed_at`) are **NEVER** overwritten or erased.

## 7. How to Run the First Expert Review Session

To execute a genuine polar-mariner domain review session:

1. **Start POLARIS Backend:**
   ```powershell
   .\laya\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8001
   ```
2. **Open Domain Review Portal:**
   Navigate to `http://127.0.0.1:8001/review` in a browser.
3. **Enter Reviewer ID:**
   Enter your assigned ID (e.g., `REV_001` or `REV_CAPT_SMITH`). The ID is automatically saved in browser session storage.
4. **Begin Priority Queue:**
   The portal loads the top-100 highest-priority cases sorted by risk ranking (Emergency, Heavy Ice, Blocked Route, Low Visibility).
5. **Independently Assess Scenario:**
   - Review vessel kinematics, ice concentration, iceberg proximity, and environmental vectors.
   - Inspect environmental data sources (USNIC, CMEMS, ERA5).
   - Evaluate the software baseline recommendation (`NOT EXPERT VALIDATED`).
6. **Submit Annotation:**
   - Select your primary recommended maneuver (`CONTINUE`, `SLOW DOWN`, `REROUTE`, `HOLD POSITION`, `REQUEST ESCORT`, `EMERGENCY RESPONSE`, or `AMBIGUOUS`).
   - Assign professional confidence rating (1–5).
   - Check key driving evidence factors.
   - Enter decision rationale and optional additional information requests.
   - Click **Save Expert Annotation**. Confirmation toast **`SAVED`** appears.
## 8. Automated Three-Source Hybrid Labeling & Human-in-the-Loop Triage

### Three-Source Adjudication Architecture (`backend/polaris_label_adjudicator.py`)
POLARIS employs a rigorous three-source evidence adjudication layer to process domain scenarios without generating fake expert reviews:

1. **Source A:** POLARIS Experimental Rule Baseline Action
2. **Source B:** Laya Neural Model Prediction & Confidence
3. **Source C:** POLARIS Physics & Hydrographic Simulation Engine Outcome

```text
                  ┌──────────────────────────────────────────────┐
                  │          POLARIS Domain Scenario             │
                  └───────┬──────────────┬──────────────┬────────┘
                          │              │              │
                          ▼              ▼              ▼
                    ┌───────────┐  ┌───────────┐  ┌───────────┐
                    │ Source A  │  │ Source B  │  │ Source C  │
                    │ Rule      │  │ Laya      │  │ Simulation│
                    │ Baseline  │  │ Prediction│  │ Engine    │
                    └─────┬─────┘  └─────┬─────┘  └─────┬─────┘
                          │              │              │
                          └──────────────┼──────────────┘
                                         ▼
                          ┌─────────────────────────────┐
                          │   Three-Source Agreement    │
                          │   & Safety Gate             │
                          └──────────────┬──────────────┘
                                         │
                   ┌─────────────────────┴─────────────────────┐
                   ▼                                           ▼
         [SILVER ACCEPTANCE]                         [HUMAN REVIEW QUEUE]
 - 3 Sources Agree                            - Baseline/Laya/Sim Conflict
 - No High-Consequence Action                 - Low Laya Conf (<0.60)
 - Conf >= 0.60, No Emergency                 - Emergency / Blocked Route
 - Physical Clearance >= 300m                 - High Hazard (>= 1.5)
 - expert_validated = false                   - High-Consequence Maneuver
```

### Silver Acceptance Gate Rules
- **SILVER Labels (`AUTO_ACCEPT`):** Generated automatically **ONLY** when:
  1. All three automated sources (Baseline, Laya, Simulation Safety Engine) strictly agree.
  2. The candidate action is **NOT** a high-consequence action (`emergency_response`, `hold_position`, `request_escort`).
  3. Laya decision confidence $\ge 0.60$.
  4. No route blockage, active emergency, high hazard score ($\ge 1.5$), critical iceberg proximity ($< 300\text{m}$), or poor visibility ($< 1.0\text{ NM}$).
  5. Provenance is complete and data schema is valid.
  $$\text{label\_type} = \text{SILVER}, \quad \text{expert\_validated} = \text{false}$$
- **Prohibited High-Consequence Auto-Acceptance:** High-consequence actions (`emergency_response`, `hold_position`, `request_escort`) are **NEVER** auto-accepted into SILVER labels based on automated agreement alone, and must always be routed to `HUMAN_REVIEW_REQUIRED`.
- **HUMAN_REVIEW_REQUIRED:** Assigned whenever any automated source conflicts, Laya confidence is low ($< 0.60$), high-consequence action is triggered, route is blocked, active emergency is declared, or hazard severity $\ge 1.5$.
- **AMBIGUOUS / INVALID:** Assigned when scenario family is conflicting/ambiguous or data quality defects are detected.
- **GOLD Labels:** Created **EXCLUSIVELY** when a genuine polar-maritime expert annotates a scenario via the Review Portal (`http://127.0.0.1:8001/review`).
  $$\text{label\_type} = \text{GOLD}, \quad \text{expert\_validated} = \text{true}$$

### Review Priority Score (RPS) Formula
Scenarios in the human review queue are dynamically ordered by a transparent Review Priority Score $S \in [0.0, 100.0]$:
$$S = \min\left(100.0, \; S_{\text{disagree}} + S_{\text{sim\_conflict}} + S_{\text{high\_consequence}} + S_{\text{low\_conf}} + S_{\text{emergency}} + S_{\text{blocked}} + S_{\text{hazard}} + S_{\text{proximity}} + S_{\text{visibility}} + S_{\text{fuel}}\right)$$

- **Baseline vs Laya Disagreement ($+30$):** Baseline action $\neq$ Laya prediction
- **Simulation Safety Conflict ($+35$):** Simulation engine flags major safety violation or collision
- **High-Consequence Maneuver ($+25$):** Action is `emergency_response`, `hold_position`, or `request_escort`
- **Low Laya Confidence ($+20$):** Laya decision confidence $< 0.60$
- **Active Emergency ($+20$):** Active emergency protocol declared
- **Route Blocked ($+15$):** Segment blocked by iceberg or heavy pack ice
- **High Hazard Severity ($+15$):** Hazard severity score $\ge 1.5$
- **Critical Iceberg Proximity ($+10$):** Iceberg distance $< 300\text{m}$
- **Poor Visibility ($+10$):** Visibility $< 1.0\text{ NM}$
- **Low Fuel ($+10$):** Remaining fuel $< 20\%$

### Audit for Circularity & Independence
> [!NOTE]
> **Circularity Audit Finding:** The experimental baseline rule engine (`scratch/polaris_rule_baseline.py`) and the simulation safety validator (`backend/route_validation.py`) share spatial collision geometry definitions (e.g. 300m iceberg exclusion envelope and Nomoto response limits). Thus, while simulation validation confirms physical consistency within POLARIS physics parameters, **it does NOT constitute independent expert ground truth**. Consequently, auto-accepted labels remain explicitly designated as `SILVER` (`expert_validated = false`), and `GOLD` status requires genuine human watch-officer review.

### Dataset Storage Hierarchy (`data/decision/`)
- `silver/polaris_silver_scenarios.jsonl`: Auto-accepted SILVER labeled scenarios (`expert_validated = false`).
- `gold/polaris_gold_scenarios.jsonl`: Genuine expert-annotated GOLD scenarios (`expert_validated = true`). Starts at 0.
- `review_queue/review_package_auto_priority.jsonl` & `.csv`: Auto-prioritized human review queue.
- `review_queue/triage_manifest.json`: Automated triage report preserving full three-source evidence.
- `holdout/polaris_benchmark_holdout.json`: 100% isolated 10-case evaluation benchmark.
